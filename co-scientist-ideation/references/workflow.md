# Six-Block Supervisor Workflow

## Core rule

Use scientific meaning as the control surface. The parent Supervisor keeps the current run bounded,
admits readable scientific records, and preserves uncertainty. Headings and short IDs help bind claims,
reviews, and lineage; they do not determine scientific quality.

```text
Block 1  Goal + Evidence Map
→ Block 2  Multi-strategy Generation
→ Block 3  Reflection + Deep Verification
→ Block 4  Proximity + Ranking [conditional]
→ Block 5  Evolution + Fresh Reflection
→ Block 6  Meta-review + Human Selection
```

Block 5 may return a reviewed descendant to Block 4 only when comparison can change the decision.
Block 6 ends the current run. It never reopens an earlier block automatically.

## Admission, stage value, independence, and failure isolation

Admit the smallest scientific unit that can stand on its own: one evidence claim, candidate, Review
Record, comparison, or descendant. A malformed or scientifically invalid item does not invalidate
valid siblings.

- The Supervisor may omit or mark a local item `unvalidated`; it must not rewrite a producer's
  scientific claim or judgment.
- A candidate does not review itself. A descendant author does not perform its fresh review.
- A comparator does not see author identity, generation lens, current preference, or prior rank.
- Supervisor synthesis is not independent Review, comparison, or completed Evolution.
- Already-seen invalid content cannot become cognitively unseen. Disclose possible diagnostic influence
  when it could affect the final package, without granting that content scientific authority.

Before an optional call, freeze its decision, distinct authority, possible state/routing change, and
legal skip. Call only if the parent lacks that authority and the return can change a scientific
decision or material stop; root and fresh Reviews remain mandatory. Admit the smallest valid return.
Without a delta, do not derive a follow-up. Existing `skip`, `No-repair`, `no-finalist`, and workflow
failure remain valid outcomes.

When cost matters, Block 1 freezes finite attempts. Capacity/transport/malformed failure consumes one;
retry must be preallocated. Exhaustion takes the existing failure route; only a new user decision may
expand the plan. Never backfill quota or switch provider/model automatically. Continuation retains the
same authority lineage.

Reject or downgrade only the affected item for a missing mechanism, falsifier, evidence premise,
formal check, feasible measurement, local citation, or readable section. A candidate-local safety or
ethics problem rejects that candidate and prohibits its downstream use while preserving unrelated
siblings. A fabricated citation local to one object invalidates that object and triggers a bounded
check of shared evidence.

Stop the whole run for an unsafe or unauthorized goal; privacy or privileged-information exposure;
contamination by unavailable solution material or prior outputs; shared-evidence fabrication or
systemic contamination; material goal drift; no usable evidence/observation anchor; or a missing human
decision that changes safety, scientific validity, authorization, cost, or scope.

## Block 1 — Goal + Evidence Map

### Entry and ownership

Begin from a research direction, observation, anomaly, opportunity, or question. Freeze only the
decisions needed to define the scientific search space:

- domain, intended contribution, and central question;
- observed/reported anchor and why it matters if real;
- what novelty means for this task;
- permitted sources, retrieval surfaces, date/corpus boundary, and run-scoped offline/web policy;
- available data, measurements, methods, compute, time, cost, and expertise;
- safety, ethics, privacy, and unpublished-material boundary;
- desired Decision Package, candidate budget, and finite role attempts when cost matters.

Ask the user only when an answer changes scientific validity, safety, privacy, authorization, cost,
or scope. A preferred module or metric is not a problem anchor. Mine the problem before proposing a
solution.

### Progressive retrieval

1. Inventory the authorized corpus or search space and its run-scoped offline/web boundary.
2. When Web retrieval is authorized and decision-relevant, open primary or authoritative sources;
   keep unpublished or private query content abstract unless authorized.
3. Treat snippets as leads; admit only opened claim-uses with source identity, location,
   scope, relation, and limitation.
4. Screen enough material to identify source families and plausible explanations.
5. Deep-read only sources that can change the problem framing or discriminate explanations.
6. Preserve supporting, contradictory, limiting, negative, null, and unresolved evidence.
7. For every reported exact quantity or named-source comparison, bind the exact source, claim, and
   location required by the quantitative/citation gate in `contracts.md`.
8. Stop broad retrieval when the problem map is decision-sufficient.
9. Reserve candidate-specific nearest-collision searches for Block 3.

Prefer primary papers, official datasets and documentation, standards, original repositories, and
scientist-provided observations with explicit provenance. Secondary material supplies context when
primary sources are unavailable; it does not establish a technical mechanism by itself. Repeated
claims from one source family remain one source family.

Keep these epistemic types explicit in readable prose: **Fact**, **Interpretation**, **Hypothesis**,
**Prediction**, and **Design choice**. Each claim has one canonical evidence binding. A failed search
or corpus absence is not evidence of novelty.

### Problem mining

Look for consequential contradictions, anomalies, omitted measurements, boundary failures, scaling or
time effects, unexplained successes, untested causal attributions, trapped general principles, and gaps
between endpoint metrics and the claimed internal process. Keep at least one competing explanation or
unresolved tension visible.

### Exit

Advance only when the Goal–Evidence Map contains a consequential problem or testable opportunity, at
least one usable evidence or observation anchor, separated facts and hypotheses, a visible alternative
or gap, known resource and evidence boundaries, and no run-level stop. Generation must not need to
assume the desired answer.

Stop honestly when there is no usable anchor, the only gap is corpus absence, nearest work already
solves the same function and boundary, the anchor is known false, the required measurement is
unavailable, private material cannot be handled safely, or no scientific question can be mined from a
solution-first request. State the smallest evidence that could reopen ideation.

## Block 2 — Multi-strategy Generation

### Inputs and lenses

Every generator receives the same frozen core boundary plus its explicit record-access overlay; peer
drafts remain invisible.

Apply the shared Stage Value test, then choose from these temporary lenses:

- **Mechanism:** shortest explanatory account, causal seam when claimed, and predicted intermediate.
- **Falsifier/discriminator:** risky prediction, cheapest decisive measurement, control, and rejection result.
- **Boundary/transfer:** reversed assumption or transferable principle, structural correspondence,
  analogy-break boundary, and target-specific prediction.

These are cognitive strategies, not permanent Agents or separate workflow stages.

### Candidate construction

Produce normally 2–4 total candidates. For each candidate:

1. bind it to the evidence-backed problem pressure and value;
2. state whether it is general or causal/mechanistic;
3. write one shortest explanatory spine;
4. name the nearest functional prior and exact delta, or say `unknown`;
5. expose decisive assumptions and a strong alternative explanation;
6. derive a prediction that differs from the alternative;
7. state a direct falsifier, boundary, failure mode, and cheapest discriminator;
8. check resource and safety fit;
9. apply the quantitative/citation gate to every reported number, benchmark, prevalence/usage claim,
   date, rank, and named-source comparison;
10. remove paper/module names and confirm that the scientific claim remains.

For a causal/mechanistic claim, include the intervention seam, entities/state, direction, intermediate
mediator or trajectory, an appropriate identity/no-op/counterfactual/matched control, a wrong-reason
alternative, and a mechanism-targeting falsifier. Do not force causal language onto observational,
predictive, structural, or formal hypotheses.

For cross-domain transfer, bind source problem → transferable principle → target evidence pressure →
structural correspondence → what is not transferred → analogy-break boundary → target-specific
prediction/falsifier → nearest target alternative.

For an algorithmic, systems, formal, numerical, or operator-semantic claim, add the conditional
Constructive Contract defined in `contracts.md`. Do not force it onto ordinary empirical claims.

### Anti-stitching and ownership

Apply the name-removal, functional-replacement, and single-spine tests. Component recombination is
admissible only when the joint operation creates one necessary target-specific explanation and a
prediction no component alone implies.

For a multi-component claim, only when the live candidate has genuinely separable components, name
the claimed bottleneck and keep decision-relevant quality and resource conditions matched. Define one
component-isolation discriminator and one component-local falsifier; isolated component success does
not prove the joint claim.

The Generator proposes claims, assumptions, predictions, and any base/candidate/off condition. It
does not self-certify novelty, formal or dimensional validity, Reviewer verdicts, ranking, or closure.
Formal and dimensional validity is Reviewer-owned in Block 3.

Admit cards independently. Minor Markdown variation is not a scientific failure. A missing critical
scientific section makes only that card incomplete or rejected. Continue with at least two distinct
cards; with one valid card, proceed to Block 3 while disclosing that diversity and comparison claims
are unavailable; with none, stop and hand the failure to Block 6.

## Block 3 — Reflection + Deep Verification

### Independent review

Give each admitted candidate one independent Review Record. The Reviewer receives the frozen Goal–
Evidence Map and candidate-specific retrieval envelope, without author identity, current preference,
or rank. One call may review several candidates for efficiency, but admit each Review Record
independently so valid siblings survive.

### Review strategies

1. **Initial review:** goal, problem value, obvious contradictions, one spine, testability, resource
   fit, safety, and obvious stitching.
2. **Evidence/collision review:** nearest work, mechanism synonyms, functional equivalence, negative
   results, counterexamples, and source-claim alignment. Empty search keeps novelty unknown.
3. **Quantitative/citation review:** audit each exact quantity and named-source comparison against its
   bound source and location. Wrong-source or unsupported decisive detail is a killer objection;
   memory, snippets, and agreement are not evidence.
4. **Deep verification:** decompose decisive assumptions; mark each established, supported, uncertain,
   contradicted, or untested; name the observation that decides it.
5. **Bidirectional steelman:** strongest support, strongest opposition, exact shared disagreement, and
   the smallest decision variable that changes the verdict.
6. **Wrong-reason simulation:** trace whether shortcut, leakage, capacity, calibration, normalization,
   optimization, unstable measurement, or parameterization could explain success.
7. **Formal/causal/constructive verification when applicable:** calculate dimensions, residuals,
   identities, invariances, controls, mediator trajectory, necessity, temporal order, and
   counterexamples. For a triggered Constructive Contract, verify its state, invariant, update,
   resource/precision bound, proof obligation, and implementation delta. For a qualifying
   multi-component claim, check whether matched isolation separates the live components; isolated
   success is not joint validity. Persuasive prose and a Generator-proposed off
   condition are not declarations of validity.

Evidence belongs once beside the premise it bears on. Unsupported decisive premises are downgraded
locally; conflicting evidence stays visible. The Reviewer does not invent citations or rewrite the card.

### Verdict and routing

Use `continue / revise / reject / insufficient evidence`:

- `continue`: coherent and testable with no known decisive contradiction; not a claim of truth or novelty;
- `revise`: worthwhile core blocked by one exact killer objection, with repairable scientific fields;
- `reject`: absent/false spine, functional prior collision, stitching, false premise, non-discriminating
  prediction, infeasible measurement, candidate-local safety failure, or ordinary alternative that
  removes the target-specific delta;
- `insufficient evidence`: coherent but a named missing source or measurement prevents disposition.

Every review identifies strongest support, strongest opposition, decisive assumptions, nearest
collision, alternative explanations, one killer objection, repairable fields, cheapest decisive test,
and what evidence would change the verdict.

Route `continue` to Block 4 when comparison matters, otherwise Block 6. Route `revise` to Block 4 only
when several repairable candidates compete; otherwise Block 5. Retain `reject` as a rejected
alternative. Send `insufficient evidence` to Block 6 unless one bounded authorized lookup can decide it.
If zero authoritative Reviews exist, keep candidates unreviewed/unvalidated and send an honest
workflow-failure package to Block 6; Supervisor synthesis cannot substitute.

## Block 4 — Proximity + Ranking (conditional)

### Run or skip

Run Block 4 only when at least two candidates have authoritative Block 3 reviews, at least two remain
viable or repairable, and comparison can change which candidate is evolved, retained, or presented.
Skip when only one remains, all are rejected, candidates answer different questions, evidence cannot
support comparison, or the choice is an irreducible human value preference. Record the skip reason.

### Proximity

Cluster by problem object, explanatory/mechanism family, intervention seam when applicable, predicted
intermediate, decisive measurement, boundary, and nearest-work relation. Shared words or components
are insufficient. Mark pairs as duplicate, compatible variant, or distinct family. Preserve distinct
minority directions as option value.

### Bounded comparison

For a consequential pair, blind author/preference identity, compare against the same goal/evidence/
review boundary, and reverse A/B order when order bias could change allocation. Normalize by candidate
identity and stop on disagreement. Qualitative outcomes are `left`, `right`, `tie`, `reject_both`,
`insufficient_evidence`, or `order_unstable` after reversal. A comparison allocates attention; it does
not establish truth, novelty, or confidence. Hard scientific failures override presentation quality.

No total order is required. Select at most one primary repair target by default, a second only for a
genuinely different high-value mechanism when budget permits, and optionally retain one clean reviewed
candidate unchanged.

If Evolution allocation among `revise` candidates is unresolved, send every affected candidate to
Block 6 as unranked repair-target alternatives, not finalists. If final selection among eligible
`continue` candidates is unresolved, send every eligible candidate to Block 6 without Supervisor
ordering or truncation and name the missing human decision variable.

## Block 5 — Evolution + Fresh Reflection

### Branch decision and repair target

Enter with an authoritative parent Review and decide whether to create a descendant or record no
repair. A descendant requires an exact killer objection, a plausibly repairable path inside the frozen
goal/resources, and an available non-author fresh Reviewer.

The repair target binds:

```text
Parent candidate
Authoritative Review
Exact killer objection and why it blocks the parent
Scientific fields allowed to change
Evidence and constraints that remain fixed
```

Make one coherent material scientific change to problem framing, explanatory mechanism, decisive
assumption, prediction, falsifier, boundary, discrimination design, feasibility strategy, or
decision-relevant grounding. Title, terminology, prose, formatting, copied Reviewer language,
evidence-ID-only edits, score changes, or an added component without changed scientific function do
not count. Preserve the parent and state what changed and what was deliberately preserved.

### Fresh independent review

Every created descendant receives a complete non-author Block 3 review using the unchanged goal and
constraints, the parent, original Review, exact objection, changed fields, and any new evidence. Do
not tell the Reviewer that improvement is expected. The review decides whether the change is
`improved`, `partially improved`, `not improved`, or `diverged`, and whether parent, descendant, both,
or neither proceeds. A diverged descendant's complete fresh Block 3 review is its normal review; do
not add a ceremonial second review.

### Legal exits

- **Descendant:** preserve parent, exact objection, material descendant, complete fresh Review, outcome,
  and routing. A descendant needs a fresh current `continue` Review before finalist eligibility.
- **No-repair:** preserve parent and Review, exact objection, concrete fatal/not-repairable/not-worth-
  budget reason, and reject or retain-as-unresolved disposition. There is no descendant or fresh review,
  and completed Evolution is not claimed.
- **Descendant-review failure:** if a descendant exists but fresh independent Review is unavailable,
  fails, or is inadmissible, preserve parent and descendant, keep the descendant unvalidated, prohibit
  its comparison/finalist use, leave the parent's prior status unchanged, and disclose the workflow
  failure in Block 6. Supervisor self-review is not a substitute.

One Evolution round is default. A second requires a first material review-confirmed improvement, a
distinct repairable objection, and user budget. Normally no more than two candidates receive
Evolution. A failed branch consumes its default budget.

## Block 6 — Meta-review + Human Selection

### Synthesis authority

Begin after any scientific success, all-candidate failure, insufficient evidence, safety/resource/
expertise stop, or required producer/Review/fresh-Review failure. Ranking and Evolution may be skipped
when unnecessary if the reason is explicit.

The Supervisor may synthesize recurring strengths, failures, conflicts, assumptions, collisions,
minority views, diversity, and the next human action. Label it Supervisor synthesis. An optional
independent Meta-review perspective may help, but it is not a finalist gate and cannot grant new
scientific validity.

Before synthesis, close the fact set: every reported fact must already exist in the admitted
Goal–Evidence Map or another admitted evidence claim. The Supervisor may omit unsupported detail but
must not repair it from memory, import a new number during compression, or attach a valid citation to
a different claim. A needed new fact returns to Block 1 admission; otherwise keep it unresolved.

### Finalist eligibility

A root primary or reserve requires a current admitted independent `continue` Review. An evolved or
diverged descendant requires a complete fresh independent `continue` Review covering all Block 3
gates. Candidates marked `revise`, `reject`, `insufficient evidence`, `unreviewed`, `unvalidated`, or
`retain-as-unresolved` cannot be primary or reserve.

When final selection is resolved, present zero or one primary and at most one mechanistically distinct
reserve. Zero is honest. A reserve is not automatically the second-highest preference.

When final selection is unresolved because of `tie`, `order_unstable`, `insufficient_evidence`, no
admissible comparison, or a human value trade-off, the Supervisor must not assign primary/reserve
order or truncate the set. Present every eligible candidate with equal detail in an unranked human-
choice set, name the missing decision variable, and ask the scientist to choose at most two for later
detailed follow-up.

Keep unresolved Evolution allocation separate: list every affected `revise` candidate as an unranked
repair-target alternative with its killer objection, and ask whether the scientist wants no branch or
which at most two branches to authorize in a future bounded pass. These are not finalists.

### Decision Package and endpoint

Return a decision-dense package with the frozen problem/evidence boundary; primary and optional
reserve when eligible, or the applicable no-finalist, workflow-failure, unresolved-choice, or
repair-allocation branch. State each shared paper fact and canonical evidence binding once in the
problem map, not again per candidate. Retain nearest-work status, strongest support, killer objection,
Reviewer-driven change, fresh-review outcome, predictions, direct falsifiers, alternatives,
boundaries, cheapest discrimination design, rejected ideas, uncertainty, minority views, and the next
human decision. Remove literature retelling and workflow narration that cannot change a decision.

For material model/tool failure, state role lineage, failure class, consumed attempt, lost
authority/diversity, and decision consequence. Separate candidate failure, missing authority,
producer/fresh-review failure, transport/retrieval failure, safety/leakage stop, and optional skip. A
readable idea may survive degradation but cannot claim a Review or Evolution that did not occur.

Use calibrated language: supported, coherent, worth discriminating, unverified novelty, insufficient
evidence, or blocked—not proven, correct, or validated. End after asking the human decision. A future
pass starts only after an explicit user request with a new Block 1 boundary.

**Execution is not authorized by this Skill output.**

## Default bounds and non-platform proof

- Temporary scratch context lasts only for the current run. Persist only a user-requested artifact.
- Create no resident Agent/Manager, dispatcher, scheduler, service, queue, database, cross-run store,
  persistent memory, external API integration, experiment runner, training/wet-lab automation, or
  automatic paper pipeline.
